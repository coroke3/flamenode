## Decision D-0602-1 — Honoのtransaction・監査の置き場（2026-10-20、MIG-0303結果で精緻化）
Work Orderの Readiness「NEEDS_REFINEMENT: transaction・監査を Hono → application service のどこで行うかを MIG-0303 の結果で確定」を、MIG-0303 DONE の結果で確定する。
- MIG-0303 の確定済み境界（DB_PACKAGE_EXTRACTION_PLAN §2 / PHASE_6 L15 / API_MATRIX）:
  - `@flamenode/domain` = framework-neutral な validation / types のみ（D1・revalidate・redirect 無し）。
  - D1 書き込み・transaction・監査・enqueue = **adapter 側**（現状 `src/lib/audit/mutate.ts` の `mutateWithAudit`、drizzle ベース）。
- Hono 側（`apps/api`）の制約:
  - 別 rootDir（`apps/api/tsconfig.json`）のため `src/lib/**`（drizzle）を import 不可。
  - `@flamenode/api` package.json に drizzle 依存なし。R-API は `c.env.DB.prepare(...)` の raw D1 SQL を要求。
  - `mutateWithAudit` + `prepareAuditLogEntries`（capability / actorX / retention / snapshot / diff / CAS）は約 700 行の共有監査機構で、CURRENT の `audit_logs` 行と byte 一致を再現する唯一の実装。
- したがって U02 の「監査・Queue が CURRENT と一致」（DONE checklist）を満たすには、以下のいずれかが必要:
  - **Option A（adapter 自持）**: `apps/api` に framework-neutral な raw D1 mutation+監査 module を新設し、`mutateWithAudit` の契約（単一 D1 batch = mutation + 監査 INSERT + CAS + changes 検証 → post-commit Queue enqueue）を byte 一致で mirror。`@flamenode/domain` は validation のみ呼ぶ。自己完結だが監査ロジックを重複（「共有せず copy」に抵触する懸念）。
  - **Option B（共有 core 抽出）**: raw D1 handle で動く framework-neutral な mutation+監査 core を新規 package（例: `packages/db` / `packages/audit`）へ抽出し、`src/lib/audit/mutate.ts` を薄い drizzle wrapper に。Next action と Hono route が同一 service を呼ぶ（API_MATRIX / TASK_CARDS_2_3 「旧 Server Action と Hono で同一 service を呼ぶ」）。広範な refactor（共有 primitive の変更、113 call site 影響）、MIG-0602 owned paths 外 → 別 MIG task + lead review 必要。
- **推奨: Option B を前提にした staged 進め方。** ただし Option B の抽出は 1 micro-unit 内に収まらず、Phase 6 全 mutation task（MIG-0602/0603/0604/0605、MIG-0702）に波及する共有基盤であるため、**単独 micro-unit として静かに実装しない**。この決定（A/B の選択と B なら抽出 task の ID/依存）は **lead/owner 承認**をもって確定する。承認まで U02 実装は開始しない（「cardsにない機能を発見したら card/ledger に追加してから着手」に準拠）。
- STOP 条件との整合: 監査の strict/CAS の「意味」は変更しない（変更は不要）。変更するのは監査機構の「置き場」（adapter 共有化）のみで、STOP を踏まない。

### D-0602-1 決定（2026-10-22、Yugo「推奨で進めて」）
- **Option A を採用**（apps/api 内の raw D1 mutation + 監査 module）。Option B（共有 core 抽出）は後続 task。

- MIG-0608 follow-up（session D1 失敗 -> 503 database_unavailable、user 行欠落 -> 401、private no-store、allowLocalPreview は FLAMENODE_LOCAL_PREVIEW=1 のみ）を MIG-0602 の in-scope 修正として承認。

- 既知の差: CURRENT writeGuard は常に getApprovedXIds を呼び、失敗を `db_unavailable` にする。admin 経路の Hono は呼ばない（identityRequirement 無指定では結果を使わない）ため、その D1 失敗時の deny reason だけ異なる（Hono は deny せず通す）。active X 要件を指定した route は同一 user 読み込みに畳み込んだ approved X 判定を使う。
