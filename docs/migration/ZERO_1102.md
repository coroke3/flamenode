# 1102 ゼロ設計（実行種別ごとの CPU 予算と検証）

> Status: Active / 移行の 1102 受入基準の正本
> Last updated: 2026-10-15（D-09 決定を反映）
> 正本の分担: 計測済みの現状値は [`cloudflare/PERFORMANCE_BASELINE.md`](cloudflare/PERFORMANCE_BASELINE.md)、Phase 4 の順序は [`PERFORMANCE_IMPLEMENTATION_PLAN.md`](PERFORMANCE_IMPLEMENTATION_PLAN.md)、route 別の担当は [`PERF_HOTPATH_MATRIX.md`](PERF_HOTPATH_MATRIX.md)。**1102 の合否はこの文書で判定する。**

## 1. 1102 とは（出典）

- Worker が CPU 時間か memory の上限を超えると、Cloudflare は利用者に Error 1102（`Worker exceeded resource limits`）を返す。outcome は `exceededCpu` / `exceededMemory`。出典: https://developers.cloudflare.com/workers/platform/limits/
- Workers Free の上限は、HTTP request 1回あたり CPU 10ms、Cron Trigger 1回あたり CPU 10ms。memory は 128MB、起動（module top-level）は CPU 1s。出典: 同上。
- 「たまの超過は isolate の余裕で許されるが、常に超えると打ち切られる」と書かれている。出典: 同上。**この移行では余裕に頼らず、設計上の最大値を 10ms 未満にする。**
- Queue consumer の CPU 上限は、Cloudflare の文書の間で食い違う。Queues の limits ページは「consumer の CPU は既定 30秒（5分まで変更可）、Free と Paid で同じ（違いは message の保持期間だけ）」と書く（https://developers.cloudflare.com/queues/platform/limits/ ）。Workers の limits ページの Free の表には HTTP と Cron の 10ms しか無い。本番の実測では、`flamenode-content-jobs` の Queue consumer が CPU 50ms で `exceededCpu` になった（[`cloudflare/PERFORMANCE_BASELINE.md`](cloudflare/PERFORMANCE_BASELINE.md) の Individual production evidence、7日で推定約10件）。30秒が効いていれば 50ms では止まらないので、**この移行では Queue consumer も 10ms の上限として扱い、§3 の `B` の 8ms を「安全側の暫定予算」とする。** 8ms は確かめた上限ではない。MIG-0409 の U07（非本番で CPU を 20ms / 100ms / 1秒使う consumer を各 50回）と、MIG-0906 の G2（本番の背景処理の 7日間の観測）で確定させ、30秒が確かめられたらこの節と §3 の `B` を見直す。
- 静的 asset への request は Worker を起動せず、無料・無制限。出典: https://developers.cloudflare.com/workers/platform/pricing/ （注3）。Worker が起動しない request では 1102 は起きない。
- 待ち時間（`fetch`、D1、KV、R2 の応答待ち）は CPU 時間に入らない。D1 の結果を JS で処理する時間は入る。出典: 同上 limits の CPU time 節。

## 3. 実行種別と予算

Work Order の `- **Runtime:**` 行に、下の ID を1つ以上書く。予算は **p95 ではなく最大値**で判定する。1102 は1回ごとに判定されるので、重い入力が1種類あれば p95 が低くても起きる（例: 下の計測で Release ページは最大 500 作品・267KB を描画し 41〜44.5ms）。

| ID | 種別 | 例 | Worker | CPU 最大値の予算 | 構造上の上限（設計で守る） |
| --- | --- | --- | --- | --- | --- |
| `S0` | 静的配信 | Astro が build した HTML / JS / CSS / 画像 | 起動しない | 該当なし | `wrangler` の `assets.run_worker_first` に入れない。request 時に HTML を作らない |
| `S1` | 公開ゲートウェイ | 可視性判定、alias 解決、R2 の事前生成 HTML の返却 | 起動 | **< 5ms** | D1 0回。読み取りは KV 1回（非公開化の拒否 entry）と R2 1回（事前生成 HTML）まで。manifest の検索は O(1) か O(log n) |
| `S2` | API 参照 | Hono の GET | 起動 | **< 7ms** | D1 statement 3つまで、各 `LIMIT` は名前付き定数 100 以下。応答 64KB 以下 |
| `S3` | API 更新 | Hono の POST / PATCH / DELETE | 起動 | **< 8ms** | D1 は事前読み3つまで + `batch` 1回。他 entity への波及（通知・再生成・集計）は Queue へ 1回 enqueue するだけ |
| `S4` | session 解決 | cookie → session → 利用者 | S2/S3 の中 | S2/S3 の予算に含めて **2ms 以内** | D1 1回（MIG-0608） |
| `B` | 背景処理 | 状態を更新する Queue consumer・Cron（通知、YouTube 同期、score、cleanup）、deploy hook を呼ぶ Cron、個別ページ1件の R2 HTML 生成（MIG-0411） | 起動 | **< 8ms**（Queue consumer は安全側の暫定予算。§1） | 一覧・検索などの公開データを作らない（build 時に作る。D-09）。個別ページは1 message = 1ページ。1回の処理量は `MAX_` 定数で件数・byte を制限し、残りは D1 に残して次の message へ回す（[`IMPLEMENTATION_RECIPES.md`](IMPLEMENTATION_RECIPES.md) R-JOB） |
| `N` | 実行時コードなし | docs、test、build 時だけ動く script、UI 部品 | 起動しない | 該当なし | build 時の処理は Worker の予算に入らない。ただし build 時間を記録する |

予算を 10ms より低くしている理由: ローカル（workerd）の計測値は本番の値ではない。機械差の余裕として 2〜5ms を残す。

## 4. 設計規則（実装者が守り、レビューで確認する）

各規則は「守れているか」を diff と test で判定できる形にしている。違反が必要になったら実装せず STOP する。

1. **HTML は build 時に作る。** request 時の React / Astro 描画（SSR）は書かない。例外は D-06 の限定 SSR だけで、§5 の計測で S2 の予算を満たすこと。
2. **request で読むデータには件数と byte の上限を付ける。** D1 の query はすべて `LIMIT` を持ち、上限は `MAX_` で始まる名前付き定数にする。上限を超える入力は 400 かページングで返す。
3. **request 中に `JSON.parse` / `JSON.stringify` する対象は 64KB 以下。** 大きいデータは build 時に分割したファイルにする。
4. **request の中で他 entity へ波及させない。** 通知と集計は Queue に 1回 enqueue して返す。一覧・検索などの公開データの再生成は request でも Queue でも行わず、D1 に build 要求を1行記録するだけにする（MIG-0410 の Cron が deploy hook で build を起こす）。個別ページは、そのページの再生成を Queue に 1回 enqueue する（MIG-0411。D-09）。
5. **module の top-level で重い初期化をしない。** schema の大量生成、大きな表の構築、ファイルの読み込みは関数の中で必要時に1回だけ行う。
6. **応答は stream するか 64KB 以下にする。** 大きい body を `await res.text()` などで全部 buffer しない。
7. **cache miss で重い処理へ fallback しない。** 事前生成物が無いときは安全な 404 / 503 を返し、build 要求を記録する（D-06、D-09）。
8. **ループ・sort・正規表現は上限付きの入力にだけ使う。** 利用者の入力をそのまま正規表現にしない。
9. **計測用のコードを本番の request に常駐させない。** 計測は非本番の harness で行う。
10. **zod の版を確認する。** Cloudflare は Worker で zod を使う場合 4.5.0 以上を推奨している（古い版は schema ごとの memory が大きい。出典: §1 の limits ページ）。repo は 3.25.76（`package-lock.json` の `node_modules/zod`）。Hono API（`apps/api`）の bundle に zod を入れる前に、MIG-0601 で memory を測り、更新の要否を記録する。

## 5. 検証方法

### 非本番（各 task の DONE 条件）

- 環境: 非本番 build を `wrangler dev`（workerd）で起動し、CPU を DevTools の profiler か MIG-0606 の `+scripts/benchmark-api-cpu.mjs` で測る。手順の前例は §3 の参考表の「条件」。
- 入力は4種類を必ず含める: 通常、上限ちょうど（最大件数・最大 byte）、不正入力、cold isolate の初回。各 50回以上。
- 記録するもの: 種別 ID、入力の種類、回数、CPU の p50 / p95 / **max**、D1 statement 数、応答 byte。PR 本文と work-item に貼る。
- MIG-0606 の harness が merge されるまでに作る S2 / S3 の task は、CPU を「未計測」と書く（推定値を書かない）。予算の合否は MIG-0606 でまとめて判定する。

### 本番

- MIG-0902 の観測期間に、Worker 別・日別の Exceeded CPU / Exceeded Memory を記録する。G1 は web 系 Worker が7日連続 0件。
- 背景処理の Worker も同じ方法で記録し、G2 を判定する。旧 rebuild 経路（`workers/json-generator`）は CURRENT の Next が読む間は残るので、G2 の7日は MIG-0907 で消した後から数える。
