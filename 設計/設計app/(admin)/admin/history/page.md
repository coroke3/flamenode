# 履歴・復元管理ページ設計 (`/admin/history`)

## 2. デザイン方針

- **コンセプト**: "Timeline Oversight" (システムの歩みを可視化する)
- **レイアウト**:
    - **左側**: 管理機能全体のナビゲーションを配置する固定サイドバー。
    - **右側**: システム内で行われた全ての操作を時系列で表示するアクティビティフィード（GitHubのContribution ActivityやSlackの履歴ログのリファレンス）。
    - **上部**: タイムレンジ・エンティティ・操作種別・重要度のフィルタバーとサマリカード（直近24hの更新件数など）。
    - **詳細パネル**: 右カラムに固定される詳細ドロワーで、Diffと復元操作を完結。
- **情報設計**:
    - **エンティティ別整理**: Event / Video / Slot / User / Settings / Auth / System の7カテゴリで統一。
    - **密度制御**: リストは要約を最小限にし、詳細はドロワーで展開する二段階表示。
    - **検索スコープ**: キーワード検索は `table_name` と主要フィールドを対象にし、誤検知を抑制。
- **視覚演出**: 操作の種類（作成、更新、削除、復元）ごとに異なるアイコンと淡い背景色を使用し、スクロールするだけで操作の種類を判別可能にします。
- **ライト/ダークモード**: `FlameNode-Design-System.md` のトークンに従い、Diff（差分）表示には低彩度の緑/赤を採用。長時間の監視でも目が疲れにくい設計を行います。
- **体験**: 特定のログ行をクリックすると、詳細なJSON Diffがシームレスに展開されるアコーディオンUIを採用し、ページ遷移なしで詳細を確認できるようにします。

## 3. 目次・機能一覧

1. **システム操作ログ一覧・検索機能**: 全ての変更履歴のリスト表示
2. **エンティティ/操作種別のフィルタリング**: 大量ログを迷わず探索
3. **データ復元 (Restore) 機能**: 過去のスナップショットからの差し戻し
4. **古いログの一括削除 (Maintenance) 機能**: 保存期間を過ぎたログのバッチ削除
5. **変更内容比較 (Diff) 表示機能**: 変更前と変更後の視覚的比較
6. **サマリ/傾向の可視化**: 直近の変化量を俯瞰

## 4. 各機能の詳細解説

### 1. システム操作ログ一覧・検索機能

*   **役割:** 「いつ」「誰が」「何を」変更したかを特定する。
*   **内部ロジック:** 
    *   `history_logs` テーブルを降順（新着順）に一覧表示。
    *   `table_name`, `record_id`, `operator_discord_id` によるフィルタリング。
    *   `entity_type` を付与し、UIはカテゴリバッジで視覚的に判別。

### 2. エンティティ/操作種別のフィルタリング

*   **役割:** データの種類が多い環境でも、目的の履歴に最短到達する。
*   **内部ロジック:** 
    *   **エンティティ**: Event / Video / Slot / User / Settings / Auth / System をトグルで切替。
    *   **操作種別**: Create / Update / Delete / Restore / Assign をチップで絞り込み。
    *   **重要度**: Normal / Warning / Critical を色とアイコンで表現。

### 3. データ復元 (Restore) 機能

*   **役割:** 削除された動画の復旧や、誤った属性変更を取り消す。
*   **内部ロジック:** 
    *   選択したログの `before_data` を取得。
    *   現在のレコードを `before_data` の値で上書き（`UPDATE`）。
    *   **既存再現（高度な復習）**: `video_events` / `video_members` などの中間テーブルは JSON スナップショットから行単位で復旧し、D1 のリレーションを正確に再構成する。
    *   **注意:** 復元操作自体も新たな `history_logs` として記録される。

### 4. 古いログの一括削除 (Maintenance) 機能

*   **役割:** D1 の肥大化を抑制する。
*   **内部ロジック:** 
    *   通常ログは90日保持、X ID再申請、X ID却下、枠解放、`voided`、復旧、通知失敗、コストガード操作は180日保持に分ける。
    *   Cloudflare Workers の Cron Triggers を設定し、深夜帯に保持期間を過ぎた通常ログを削除候補化する。長期ログは180日経過後も、物理削除候補として件数と影響範囲を確認してから処理する。
    *   **既存再現**: 管理ミスを防ぐため、管理画面からも手動実行が可能で、実行前に削除予定のログ件数を表示し、最終確認を求める。

### 5. 変更内容比較 (Diff) 表示機能

*   **役割:** 具体的にどのフィールドが変更されたかを把握する。
*   **内部ロジック:** `before_data` と `after_data` の JSON を比較し、差異があるキーをハイライト表示する。
    *   **要約行**: 差分キーの数と主要フィールド名を先に表示。
    *   **ツリー表示**: JSONを折り畳み可能なツリーで表示し、深い階層も追えるようにする。

### 6. サマリ/傾向の可視化

*   **役割:** 直近の変化量と異常検知を俯瞰する。
*   **内部ロジック:**
    *   24h/7d/30d の集計カード（総変更数、削除数、復元数）。
    *   重要度の比率を小さなバーで可視化。

## 5. 詳細UIロジックとステート管理

### 5-1. 復元時の競合警告
*   復元しようとしているデータが、ログ記録時よりも後にさらに別の操作で更新されている場合、「現在のデータがログより新しいです。上書きしますか？」という警告を出し、強制上書きかキャンセルの選択を促します。

### 5-2. ログのエクスポート
*   監査や大規模なデータ調査のために、表示中のログを CSV / JSON 形式でローカルにダウンロードする機能を備えます。

### 5-3. 段階的ロードとパフォーマンス
*   直近の50件を先読みし、スクロールで追加ロード。
*   D1のクエリは `created_at` と `entity_type` に対してインデックスを前提とする。
*   Cloudflare Workersのレスポンス上限に配慮し、Diffの重いデータは必要時のみ取得する。

### 5-4. コンテキストリンク
*   ログ行から対象レコードの詳細画面へ遷移できる導線を用意。
*   ただし、削除済みレコードは復元モーダルへ誘導する。

## 6. X ID再申請・voided・コストガードの監査

- **閲覧範囲**: 管理者は全ログを確認できる。イベント編集許可者は担当イベント内のイベント設定、作品、枠、協力者権限、`x_reapply_required`、`voided` 要請に関するログだけ確認できる。
- **マスク**: 担当外ユーザーのメールアドレス、Discord連携詳細、他イベントの予約詳細はマスクする。
- **voided復旧**: `voided` からの復旧は管理者専用操作とし、イベント編集許可者は復旧要請フラグを立てるだけにする。復旧時は過去スコアを再計算対象に戻し、復旧操作自体も新しいログとして残す。
- **物理削除候補**: `voided` から180日を過ぎた作品は物理削除候補として表示できるが、削除前に関連コメント、チャプター、いいね、ブックマークの非表示保持状態と監査保持要件を確認する。
- **危険操作**: `voided`、復旧、物理削除候補処理、ステータス強制整合、コストガード一時許可は理由入力必須とし、確認文字列方式で誤操作を防ぐ。
- **部分失敗対応**: X ID却下処理などで部分失敗した場合、「枠解放のみ再試行」「ステータス強制整合」の個別アクションボタンを出す。
- **タスク優先度**: 管理画面のタスク一覧では「コストガード」→「X ID再申請」→「YouTube同期失敗」の順で優先表示する。
