## Decisions
- Decision: stacked on PR #333 to reuse `loadPersonalContext`, `computeOnboardingState`, the harness and the personal router (sessionMiddleware + requireAuth + `Cache-Control: private, no-store` + 503 handler). Edits to #333 files are exactly two lines: the `/entry` mount in `personal/index.ts` and `export * from "./entry.ts"` in contracts `personal/index.ts`.
- Decision: GET never writes. CURRENT entry pages have no write during page load (no `maybeMarkOnboardingComplete` call on these three pages), so there is no mutation handoff from them. Draft autosave / submit are the forms' own client actions (MIG-0702/0603).
- Decision: S2 budget. Every endpoint is session lookup (1) + `loadPersonalContext` (1) + ONE data statement (1) = 3 D1 statements, 0 batches, <= 8 binds, all LIMITs named constants <= 100 (ENTRY_PAGE_ROWS = 100; per-event question arms use their own LIMIT 19 / 100 inside one row per event). The data statement is a UNION ALL of arms returning `(k, j)` rows with one `json_object` (<= 64 KiB, enforced) per row. Whole response <= 64 KiB (MAX_RESPONSE_BYTES): event lists are cut by bytes and checked again before sending.
- Decision: the `redirect()` / `notFound()` calls of CURRENT slotted page become data: `200 {kind:"redirect", to}` (`/entry`, `/dashboard/edit/<video_id>`) and `404 {error:"not_found"}`. Unauthenticated -> 401, banned -> 403 (requireAuth = CURRENT requireSession / BannedNotice).
- Decision: derived presentation values stay in the UI. `submitBlock` is a code (`no_active_x | not_linked | pending | rejected | not_approved`), not the Japanese sentence. `youtube_description_event_url` is not returned: CURRENT builds it with `absoluteUrl("/event/<id>")` from `NEXT_PUBLIC_SITE_URL`, which the Worker has no binding for; the SPA derives it from `event.id` and its origin.
- Decision: extra fields are not returned (reserved_by_user_id, x_user_id of own slot rows on the index, sort_order, per-row timestamps, `allow_unslotted_posts`, user email). The index returns already-sorted `reservedSlots`; `events` is already CURRENT-sorted and CURRENT-filtered.

## Behavior differences vs CURRENT (all recorded here, none silent)
1. Logged-out `/entry` (login CTA + public active events list) is not served: 401. The SPA renders the CTA; its public events list needs the MIG-0604 public events API (handoff to MIG-0703).
2. S2 bounds (CURRENT is unbounded or up to 120/200): the three event lists (index `events`, slotted / unslotted `eventOptions`) return at most 100 rows per request and are paged with `?offset=` (0..900, anything else = 0); the response carries `truncated` and `nextOffset` (null when complete; a page of exactly 100 rows reports truncated and its continuation may be empty). Options are also cut by bytes so a response never exceeds 64 KiB; `nextOffset` continues after the last returned row. Per event: custom questions <= 18 (19 read, more -> 503 like CURRENT), stage-permission rows <= 100 (reached -> not truncated silently: still read as 100). A JSON row > 64 KiB, or one option that alone exceeds the response bound -> 503. The part of a slot is computed in SQL (window functions, `SLOT_PART_CTES`) instead of reading every slot of the event, so an event with > 100 slots no longer needs a cap; parity-tested against the real `buildSlotParts` including a 250-slot event.
3. Deterministic order where CURRENT has none: slotted `acc` events `ORDER BY id`; reserved slots tie-break `slots.id`; index `ORDER BY start_time DESC, id` before CURRENT's JS sorts (final order identical because the comparator ends on id).
4. One `now` per request (CURRENT calls `Date.now()` at several points); `fetchActiveEvents(...).catch(() => [])` is not separately swallowed: a failed data statement is 503 (CURRENT's later reservedSlots query would throw as well).
5. `getLinkedXUsersForAuthUser` rows come from the context statement (cap 200 linked X, MIG-0611). X option order uses code-unit comparison for unslotted (SQLite BINARY) and `localeCompare("ja")` for slotted, as CURRENT.
6. Visibility `normalizeEventVisibility`, `computeEventStatus`, `isAcceptingEntries`, `compareEventsByUpcomingPriority`, `buildSlotParts`, `rowToQuestion`, `stageSettings` JSON are copies of pure CURRENT functions (domain-package candidates), parity-tested against the real modules.

## Exception / Decision (needs owner)
- Decision (needs owner): when the accepting events of one view exceed 100 (index / slotted / unslotted), CURRENT shows them in one list; the API now returns them in pages (`nextOffset`). The SPA (MIG-0703) must follow `nextOffset` or show a "more" control. Index pages are filtered in JS after the SQL order, so on page 2+ the in-page order is CURRENT's order within that page only (global order across pages is SQL `start_time DESC, id`). Realistic data (< 100 accepting events) is unaffected. Owner to confirm the UI contract before MIG-0703.
- Decision (needs owner): `offset` is clamped to 900 (<= 1000 events reachable); events beyond that are not reachable. Owner may raise the clamp (cost: one OFFSET scan per page).
- Decision (needs owner): stage-permission questions per event are read up to 100 rows (CURRENT unbounded); an event with >= 100 stage-permission rows would lose the tail silently. CURRENT's own per-event limit for normal questions is 18, so this is judged unreachable.
