## Decisions
- Decision: shape = MIG-0623. Each endpoint is session (1) + `loadPersonalContext` (1) + ONE data statement (1) = 3 D1 statements, 0 batches, 0 writes, **3 bind parameters** (video id `?1`, approved X ids as one JSON array `?2`; `?NNN` numbered binds repeat without extra binds). The data statement is a `WITH v / ev / appr` + UNION ALL of arms returning `(k, j)` with ONE `json_object` per row (<= 64 KiB, enforced), every arm bounded by a named LIMIT <= 100 (101 only to detect a cut). Response <= 64 KiB (`MAX_RESPONSE_BYTES`, `assertResponseBytes`); the member / subject lists are cut by bytes with the entry helper `takeWithinBytes` (first-row rule: a first item that cannot fit fails closed = 503).
- Decision: shared files. Edits to MIG-0611 / MIG-0623-owned files are exactly two lines: the `/edit` mount in `apps/api/src/routes/personal/index.ts` and `export * from "./edit.ts"` in `packages/contracts/src/personal/index.ts` (not listed in Owned paths because MIG-0623.md still claims them; their ledger rows cite this PR's SHA).
- Decision: GET never writes. CURRENT edit pages have no write during page load. Auth: `requireAuth` (401 unauthenticated = CURRENT login redirect, 403 banned = BannedNotice) and the video's own permission check run on the server, per request, from the session's linked X IDs (never from the URL).
- Decision: CURRENT's `notFound()` (also when D1 is missing) is `404 {error:"not_found"}`. CURRENT's "編集権限がありません" panel (HTTP 200) is `200 {kind:"no_access", message, public_id}` where `public_id` is `youtube_video_id ?? id` (the page's only link target; no title, creator or any other video data is returned: IDOR test). `hasAnyEditCapability` false -> `no_access`; only privilege switches possible -> `kind:"switch_only"` (header + access inputs + attached event titles); else `kind:"edit"`.
- Decision: derived presentation stays in the UI. Returned: the 10 section flags (`access.sections`), `ownership`, `membershipHint`, `canOffer{Admin,Event}Mode`, `sectionEventSources`, `eventId`, `eventTitleForMode`, `canEditAnySection` (= `hasAnyEditableVideoFormSection`) = the inputs of `buildVideoEditPermissionViewModel` (parity-tested to give the same `editable` flags); messages are codes (`EditNotice`); `PrivilegeModeBanner` links are UI. `disabledSections` / `disabledFields` are returned as strings (they are loader output).
- Decision: `?privileged=` handled exactly like CURRENT: edit page: `admin` only for role admin, `event` only when `canUseEventPrivilegeFromAccessContext`, else normal. permissions page: an explicit value is fail-closed; without a value normal -> site admin -> event (same order). A repeated `?privileged=` (Next gives an array) is treated as absent / "normal".
- Decision: `tableAvailable` (local DB without `video_members.can_edit`) is not returned: every D1 environment has the migrated column, so it is always true (`showCollabSection` / `permissionSummary` use true).

## Behavior differences vs CURRENT (all recorded here, none silent)
1. S2 bounds (CURRENT is unbounded): public members <= 100 rows and <= 64 KiB with `membersTruncated`; collab subjects <= 100 rows with `collabTruncated` (edit) / `truncated` (permissions) and the subject / public-member lists cut by bytes; video_events <= 100; staff rows <= 100. A single JSON row > 64 KiB, or a first list item that cannot fit the response bound, is 503 `{error:"unavailable"}` (never a partial body).
2. Deterministic order where CURRENT has none: `video_events` ordered by `event_id` (CURRENT: storage order = the same for the (video_id, event_id) primary key; for > 4 attached events the 4-event snapshot slice is order-dependent in CURRENT too); `video_members` ties `order_index, rowid`; `mine` probe `ORDER BY id LIMIT 8`; collab subjects: CURRENT has no ORDER BY and its plan yields `can_edit ASC, rowid` (observed on node:sqlite with the real migrations; D1's planner could differ), reproduced in JS. When the list is cut at 100 the SQL keeps the editors first (`can_edit DESC`), so the cut drops non-editors.
3. `has_account_link` / `has_notifiable_link` are reproduced **bug-compatibly**: CURRENT's `sql\`lower(link.x_user_id) = lower(${videoMembers.x_user_id})\`` inside a single-table drizzle select renders the column bare, which binds to `link.x_user_id` inside the EXISTS, so the predicate is a tautology: every subject shows "linked" / "notifiable" as soon as ANY approved link (with a notification-enabled user) exists. The SQL has the same shape (no correlation) and a comment; the parity test pins it. See brush-up proposal.
4. Linked X cap 100 (MIG-0611 `MAX_LINKED_X_USERS`) applies to the approved X IDs used for ownership / staff / `xIdOptions`.
5. One `now` is not needed (no time-dependent read in this unit); the event options that depend on `now` are U02b.
6. The page's accepting-event titles are not returned; only the attached events' titles are (they are the only ones CURRENT looks up by id for `sectionEventSources` / `eventTitleForMode`).

## Exception / Decision (needs owner)
- Decision (needs owner): MIG-0630 is delivered in units: U01 / U02a / U03 / U04 = PR #382 (merged), U02b = this PR. After U02b only U05 (STATUS integration at merge time) remains; MIG-0703 can then render the edit form from the three endpoints.
- Decision (needs owner): U02b is a SEPARATE endpoint (`/form-options`), not part of `GET /:id`, because the form data (<= 100 event options with their questions) would put the `GET /:id` response at risk of the 64 KiB bound. It re-runs the access gate of `GET /:id` inside its own data statement (same `decideEditPage`; `?privileged=` handled identically) and returns `{kind:"no_access"}` (HTTP 200, no data) both when CURRENT would show the "編集権限がありません" panel and when CURRENT shows only the privilege-switch overview (the form is not rendered there). The SPA calls it only after `GET /:id` returned `kind:"edit"`, with the same `?privileged=`. Alternative: merge into `GET /:id` (one call, response risk).
- Decision (needs owner): truncation contract for the form data. `customAnswersTruncated` (> 100 answers, e.g. an event set with > 5 full question lists) means the answers are incomplete: the SPA must not save custom answers from it. `eventOptions` pages like Entry (`truncated` / `nextOffset` / `?offset=`, <= 100 accepting events per page, cut earlier by bytes to keep the response <= 64 KiB); the SPA merges pages by id. Realistic data (a handful of open events) fits one page.
- Decision (needs owner): the events the video is attached to are listed FIRST on page 0 (so a byte cut can never drop the current events; precedent: MIG-0623 slotted prepends the slot event), then the accepting events ordered by id. CURRENT lists the accepting events in storage order and appends the attached-only ones. The SPA must not depend on the order beyond "attached events present"; if the UI sorts, nothing changes.
- Decision (needs owner): CURRENT page errors that are thrown (more than 4 stage-permission questions or answers: `video_stage_answer_read_limit_exceeded`; more than 18 general questions in one event: `video_custom_question_read_limit_exceeded`) become 503 `{error:"unavailable"}` (CURRENT: the Next error page). Same as MIG-0623.
- Known cost: the form arms are read before the gate is evaluated (one statement, so S2's 3-statement budget holds), so a caller without edit rights still makes D1 read the accepting-event arms (<= ~1,200 row reads worst case, ~100 realistic) although nothing of it is returned. The SPA only calls this endpoint after `GET /:id` said `edit`; a 4-statement variant (gate first) would break S2 and is not done. Brush-up: cache or rate-limit if abuse is observed.
- Decision (needs owner): CURRENT's `has_account_link` / `has_notifiable_link` tautology is reproduced (behavior parity). Owner to decide whether the SPA shows the CURRENT (always "linked") or whether a separate CURRENT-fix PR corrects it first (then the Hono SQL changes to the intended `lower(link.x_user_id) = lower(m.x_user_id)`).
- Decision (needs owner): truncation contract for the SPA / MIG-0702: when `membersTruncated`, `collabTruncated` or `truncated` is true the corresponding list is incomplete and the SPA must not save members / permissions from it (read-only list + "too many rows" notice). Realistic data (a handful of members) is unaffected.
- Decision (needs owner): `no_access` is HTTP 200 data (same as CURRENT's page), not 403, so a non-owner's request is indistinguishable from an owner whose sections are all locked except by `message`. Owner may prefer 403 for the SPA.
- Known delta: video_events past 100 rows and event_staff past 100 rows are not read (judged unreachable; the access snapshot keeps only 4 events).
- S2 exception: none. Every endpoint stays at 3 statements; U02b uses 4 binds (`?1` video id, `?2` approved X IDs JSON, `?3` now, `?4` offset; numbered binds repeat without extra binds). The CURRENT chunks of 80 ids become JOIN / `IN (SELECT ...)` arms, so no chunk loop and no extra statement exists.

## U02b `GET /api/personal/edit/:id/form-options?privileged=&offset=` (this PR)
Returns what the CURRENT page passes to `VideoForm` besides the video's own values (those are in `GET /:id`): `eventOptions` (video_form_settings_json + custom_questions per event; the `SlottedEventOption` shape of MIG-0623), `customAnswers` (= `initialCustomAnswers`, keys `<event_id>:<question_key>`), `stagePermissionAnswers` (= `stagePermissionInitial`, the `custom_question_answers_json` string or null), `softwareSuggestions`, `iconCandidates`, `channelCandidates` (the last two `[]` when the video has no creator X ID, like CURRENT), plus `truncated` / `nextOffset` / `customAnswersTruncated`. Code: `apps/api/src/routes/personal/edit/formOptions.ts` (route + form arms), `data.ts` (`editStatementSql("form", extra)`: only the six access arms + the form arms; `parseDataRows` / `editDataOf` shared), `packages/contracts/src/personal/edit.ts` (`EditFormOptionsResponseSchema`). Entry helpers (`customQuestions.ts`, `formData.ts`, `rows.ts`, `sql.ts`) are imported, not copied. Auth / ban / IDOR = the shared `/api/personal` middleware + the access gate of `GET /:id` (an unknown id is 404, a stranger gets `{kind:"no_access"}` only).

Behavior differences vs CURRENT (all recorded, none silent):
1. Option order (see the owner item above) and `ORDER BY events.id` on the accepting events (CURRENT has none).
2. S2 bounds: accepting events <= 100 per page (+ attached <= 100 on page 0), answers <= 100 (`customAnswersTruncated`), response <= 64 KiB (options cut by bytes, first item that cannot fit = 503). CURRENT is unbounded.
3. CURRENT's `.limit(chunk.length)` on answers is replaced by the JOIN; an answer row whose question is not an active general question of an option event is not returned (same as CURRENT, which drops them in JS). Several answer rows for the same (event, question_key) cannot exist (primary key).
4. Stage-permission question order inside one event uses `sort_order, id` (CURRENT: storage order for ties); event order = CURRENT's `currentEventIds` order. More than 4 stage questions / answers is 503 (CURRENT throws).
5. `youtube_description_event_url` (CURRENT `absoluteUrl('/event/<id>')`) is not returned; the UI derives it from the id.
6. `xIdOptions` and `softwareLabel` are NOT repeated here (they are in `GET /:id`).
Quirks kept: the `allow_user_video_event_links` = 1 filter applies to the accepting events only (an attached event is listed whatever its status, as in CURRENT); custom answers are read for ALL option events, including accepting events the video is not attached to (a stray answer is returned); the stage answers use the attached events only.
