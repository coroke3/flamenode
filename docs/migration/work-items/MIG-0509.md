## What it does
`apps/site/scripts/produceSnapshots.ts` runs CURRENT's own R2 generators (`workers/json-generator/rebuild.ts` `rebuildTarget`) against a database handle and an in-memory bucket, then wraps what they would have written into the envelope the Phase 4 loaders verify (`schemaVersion 1`, `generation`, `key`, `visibility "public"`, `sha256` of `JSON.stringify(payload)`) and writes the manifest (`allowedKeys` = produced keys, `blockedKeys` = profile keys of creators that exist but are not publicly listable). The data rules, public-only SQL, forbidden-key sanitizing and LIMITs are CURRENT's code, not a copy.

## Database access: lead decision C' (2026-10-23)
Rejected: (B) `wrangler d1 export` in the build (the export blocks production D1 writes on a 51 MB database) and (A') a proxy Worker (about 4,500 Worker requests per build times builds per day risks the free tier). Chosen: **C'** — CURRENT's generator stays untouched as the parity oracle; a build-specific batched reader fetches the same data with set-based queries through MIG-0409's read-only REST reader.
- `apps/site/scripts/batchedUserReader.ts` (`readUserObjects`): per chunk of creators (default 25), one profile query per 90 ids, one own-works query (`ROW_NUMBER()` and `COUNT(*)` partitioned by creator, top 120 rows) and one collab query (public `video_members` joined to `videos`, partitioned by member, duplicates removed, own works excluded, top 120). It assembles `users/ID.json` and `users/ID/works|collabs/N.json` exactly as `rebuildUser` does and runs the same forbidden-key check. SELECT lists and predicates are copied from CURRENT (not exported), so drift is caught only by the parity test.
- `produceSnapshots({ mode: "batched", db })`: `db` is the read-only reader; a guard refuses anything that is not a single `SELECT`/`WITH`, counts statements and enforces `maxRemoteStatements` (default 150). The fixed targets (top sections, list, recommend, users index, rules) still run through CURRENT's generators; their tracking statements (any write, and any read of `static_artifacts` / `static_rebuild_queue`) are routed to a schema-only in-memory scratch database, so nothing but SELECTs reaches the reader.
- Request budget: about 45 fixed statements plus 2 per 25 creators plus 1 per 90 creators: roughly 45 + 60 + 9 = 115 for 737 creators (cap 150). MIG-0409 reader cap (19) was written for the events index only and must be raised to about 150 for this producer; that is a one-line owner decision at the integration point, recorded here. The REST reader itself is on `mig-0409-build-time-public-data` (not merged into this stack): it plugs in as the `db` argument (`prepare(sql).bind(...).all()`); that wiring and the token are MIG-0509 proper.
- Parity: `scripts/migration-snapshot-producers.test.mjs` runs the oracle producer and the batched producer on the same seed with `creatorsPerQuery` 1, 2 and 25: every snapshot (key, bytes, sha256) and the manifest are byte-identical; no tracking statement reaches the reader; the cap is enforced. The seed has collabs from several creators, a duplicate member row, a non-public member and an own work listed as member.
- Known gap: ties in `ORDER BY scheduled_time DESC, created_at DESC` are undefined in CURRENT and in the batched query; an exact tie could order differently on production data. If production has such ties, add a deterministic `id` tiebreak to both (CURRENT change, separate task).
- The CLI keeps `--sqlite` / `--sql-dump` for tests and local runs (`--batched` selects the batched mode on them); it never contacts Cloudflare.
- Event kinds: MIG-0502 is still in progress; add them when `migration/mig-0502-event-routes` exists.

## Budget (local seed, not production)
- D1 statements: counted by the producer (`report.d1Statements`, asserted < 120 for 3 creators / 32 videos); about 6 per creator plus about 45 fixed.
- Objects: all < 2 MiB (asserted); same seed and clock give byte-identical output (asserted).
- Build minutes (MIG-0409 formula) are not re-measured: the real figure needs the production counts and the chosen access route.

## Characterization (producer -> loader -> page model)
- Envelopes verify with the real loaders (`loadAboutStatsForBuild`, `loadListingForBuild`, `loadTopForBuild`, `userPayloadSourceFromEnv`).
- User profile/works/pages equal the objects CURRENT's generator writes for the same seed (normalized with CURRENT's cores).
- Visibility: private works, the private event id and title, and the non-listable creator's profile text are in no snapshot; the creator has no user-profile object and is in `blockedKeys`. (Public videos credited to a non-listable creator stay in list/top, as in CURRENT.)
- Tampering: a changed payload fails with `HASH_MISMATCH`, another generation with `GENERATION_MISMATCH`.
- e2e: a real `astro build` from the produced directory emits `/user/creator_a`, its portfolio, `/user`, `/`, `/about` and no page for the banned creator.

## Known limits
1. Trending needs the GA4 object from the pipeline; the producer does not call GA4.
2. The date-sensitive parts (nostalgia shuffle day, `generated_at`) use the injected clock (`--now`); the top shuffle uses an in-memory KV, so its daily pick is seeded per run.
3. `users_index` over 2 MiB must be split before it can be a snapshot (loader limit); not hit at 737 creators.
4. Event kinds, video detail kinds (`snapshot/video/ID.json`) and route-shard inputs are out of this pre-work.
